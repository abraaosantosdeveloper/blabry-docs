# Modelo 3C — Abordagens Preliminares

O modelo 3C (Cartão, Conversa e Confirmação) foi utilizado para documentar as histórias de usuário do Blabry. Cada requisito passou por uma conversa entre o P.O e o desenvolvedor antes de ser implementado, garantindo clareza nos critérios de aceitação.

Esta seção registra as abordagens preliminares sobre requisitos não funcionais relacionados ao frontend — performance, responsividade, acessibilidade, segurança e manutenibilidade.

---

## Fonte única das nacionalidades

### Cartão

| Campo | Descrição |
|---|---|
| ID | RF17 |
| Como | usuário do Blabry |
| Quero | escolher minha nacionalidade em uma lista confiável durante o cadastro |
| Para | concluir o cadastro sem receber erro por ter escolhido uma opção inválida |

### Conversa

<ChatLog messages={[
    { autor: 'po', texto: 'A lista de países é enorme e praticamente nunca muda. Por que não deixar essas opções fixas no próprio formulário do frontend? Seria uma requisição a menos, e a tela de cadastro carregaria mais rápido.' },
    { autor: 'dev', texto: 'Seria, mas o banco não aceitaria. A coluna de nacionalidade do usuário é chave estrangeira para a tabela de países, então o banco só grava um código que exista lá. Se o formulário oferecesse uma opção que não está cadastrada, o usuário preencheria tudo, clicaria em criar conta e receberia um erro sem entender o motivo. A lista precisa sair do mesmo lugar que valida o dado.' },
    { autor: 'po', texto: 'Então o banco vira a fonte da verdade. Mas e se alguém enviar um código inválido direto para a API, sem passar pela tela?' },
    { autor: 'dev', texto: 'Aí a própria chave estrangeira recusa a inserção. É essa a vantagem de manter a restrição no banco em vez de só no formulário: o formulário é conveniência para o usuário, a chave estrangeira é a garantia. Duas camadas, com a mais interna sendo a que não dá para burlar.' },
    { autor: 'po', texto: 'E a rota que devolve essa lista precisa de login?' },
    { autor: 'dev', texto: 'Não pode precisar. Quem está se cadastrando ainda não tem token. Ela fica registrada antes do middleware de autenticação, junto com as rotas de login e cadastro.' }
]} />

### Confirmação

| Critério de aceitação | Verificação | Resultado |
|---|---|---|
| A lista vem do banco, não do cliente | `GET /countries` consulta a tabela `countries` | Atendido |
| A rota é acessível sem autenticação | Requisição sem cabeçalho `Authorization` | 200 |
| O formato devolvido é `{ country, name }` | Comparação da resposta com o formato esperado | Atendido |
| Nenhum campo interno é exposto | Ausência de `id` na resposta | Atendido |

Verificado em `tests/routes/countries.test.js`.

## Proteção das credenciais de acesso

### Cartão

| Campo | Descrição |
|---|---|
| ID | RNF-B01, RNF-B02, RNF-B04 |
| Como | usuário do Blabry |
| Quero | que minha senha permaneça inacessível, mesmo para quem tenha acesso ao banco de dados |
| Para | não ter minha conta comprometida caso os dados da aplicação vazem |

### Conversa

<ChatLog messages={[
    { autor: 'po', texto: 'A senha é guardada criptografada, certo? Se alguém conseguisse acesso ao banco, conseguiria descobrir as senhas dos usuários?' },
    { autor: 'dev', texto: 'Ela não é criptografada, é transformada em hash com bcrypt, o que é diferente. Criptografia é reversível com a chave; hash não tem volta. Nem eu consigo descobrir a senha de um usuário. Na hora do login eu aplico o mesmo processo na senha digitada e comparo os resultados.' },
    { autor: 'po', texto: 'E existe risco de esse hash acabar aparecendo em algum lugar por engano? Numa resposta da API, num log?' },
    { autor: 'dev', texto: 'Esse era o risco real, e por isso o hash deixou de ser um campo comum do objeto de usuário. Ele foi definido como propriedade não enumerável, então não aparece ao converter o objeto para JSON, nem ao copiar o objeto, nem ao imprimir no console. Continua acessível para quem pedir por ele explicitamente, que é o que a verificação de senha faz. A ideia é que vazar exija uma ação deliberada, em vez de depender de eu lembrar de remover o campo em cada resposta.' },
    { autor: 'po', texto: 'Quando alguém erra o login, a mensagem deveria dizer se o problema foi o e-mail ou a senha? Ajudaria o usuário a se corrigir.' },
    { autor: 'dev', texto: 'Ajudaria o usuário e também ajudaria um atacante. Se a mensagem distingue os dois casos, qualquer pessoa consegue descobrir quais e-mails têm conta na plataforma, testando um por um. A mensagem é a mesma nos dois casos: credenciais inválidas.' }
]} />

### Confirmação

| Critério de aceitação | Verificação | Resultado |
|---|---|---|
| A senha é armazenada como hash bcrypt | Comparação de senha correta e incorreta contra o hash | Atendido |
| O hash não aparece ao serializar o usuário | `JSON.stringify` do objeto e da resposta da API | Ausente |
| O hash não aparece ao copiar o objeto | Espalhamento do objeto de usuário | Ausente |
| O hash permanece acessível internamente | Acesso explícito ao campo | Atendido |
| A resposta de erro não revela se o e-mail existe | Comparação entre resposta de senha incorreta e de e-mail inexistente | Idênticas |

Verificado em `tests/models/user.test.js` e `tests/routes/auth.test.js`.

    { autor: 'dev', texto: 'A regra não fica na tela nem em cada rota, fica no próprio modelo de usuário. Qualquer rota nova que devolva um perfil passa por ali; o padrão é esconder.' },
    { autor: 'po', texto: 'E se eu abrir o meu próprio perfil pelo endereço público, com o meu @ na URL?' },
    { autor: 'dev', texto: 'Continua sendo o seu perfil, então os dados aparecem. A comparação é feita entre o dono do perfil e o usuário autenticado, não entre endereços.' }

### Confirmação

| Critério de aceitação | Verificação | Resultado |
|---|---|---|
| E-mail e nascimento ficam ocultos no perfil público | Serialização de perfil de terceiro | `null` |
| E-mail e nascimento aparecem no próprio perfil | Serialização do perfil do dono | Atendido |
| Nacionalidade permanece pública | Presença do campo em ambos os casos | Atendido |
| O identificador do usuário vem do token, nunca da requisição | Rota `/users/me` sem parâmetro de identificação | Atendido |
| A data de nascimento não sofre conversão de fuso | Serialização de data armazenada em UTC | Data preservada |

Verificado em `tests/models/user.test.js` e `tests/repositories/usuarios.repository.test.js`.
